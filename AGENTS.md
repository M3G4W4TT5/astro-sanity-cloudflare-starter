# Starting a client site from this template

This repository is a neutral public starter. A generated client repository is independent. Treat the brief, approved design, content, language, domain, accounts, ownership, mail, legal text and launch date as **per-client decisions**. Never turn the demo into a production page by changing only the title.

1. Collect the client brief, audience, pages, interaction needs, languages, content owners, accessibility needs and visual references. Record what is approved and what remains open. Ask for approval before publishing client identity, claims, assets, legal text or a domain change.
2. Inventory the client's GitHub, Sanity, Cloudflare, domain registrar/DNS, current MX/mail provider, existing business inbox, Resend or Cloudflare Email Service account, Turnstile and approved assets. Record named owners and recovery/access arrangements. Do not create substitute accounts or an inbox without a decision.
3. Generate an independent repository from the template. Replace the demo page and its `noindex` treatment with approved site-specific design and content. Adapt the small Sanity schema to actual editorial needs; add React islands only for interactions that need client hydration. Keep source evidence and uncleared assets outside Git, Pages public assets and public Sanity datasets.
4. Create a client Sanity project/dataset and set the public build identifiers. Invite named editors, establish a trusted publisher, deploy or configure Studio for the client, publish the required `home` document and verify a local static build. Sanity Free public datasets expose published documents; drafts and asset URLs have different visibility properties. Review fields and media before upload/publication.
5. Create a client Cloudflare Pages project from the client GitHub repository. Configure Node 24, the build/output settings from README, build variables and a generated `*.pages.dev` review hostname. Set `SITE_URL` for the current review origin. Keep the real domain and DNS change for the approved delivery step.
6. Create a production Pages deploy hook. Store its URL only in a Sanity webhook configured on the intended dataset: published create/update/delete, drafts and versions excluded, POST method. Test publish and unpublish. Inspect Sanity attempts, the matching Pages deployment and the live page; a successful hook request alone is insufficient. Set and test a Cloudflare Pages project update alert filtered to production deployment failures, delivered to a monitored inbox.
7. Choose the existing business inbox as contact recipient, or make inbox selection a separate decision. Choose Resend Free by default and verify the fixed sending domain/address. If using Cloudflare verified-destination sending, confirm its sending domain and verified destination first. Inspect existing MX records before any Email Routing change, especially on Google Workspace or another mail host. Configure Turnstile allowed hostnames and secret, mail provider secrets and server-side enable switch. Keep the public form disabled until a hosted submission reaches the intended inbox and Reply-To works. Verify invalid/spam cases and failure messaging. Do not store contact messages in Git or Sanity.
8. Review legal/privacy copy with the client for their actual controller, form fields, processors, retention, rights and jurisdiction. This template intentionally has no generic publishable policy. Review final content, links, accessibility, mobile layout, indexing and domain/DNS plan. Obtain client approval for launch-sensitive changes.
9. Handoff named ownership, repository and Studio access, Pages/Sanity settings, webhook and alert locations, mail provider and recipient, DNS records, renewal/cost limits, content workflow, restore/export plan and incident path. Record a representative CMS edit that reached the live site. Use `docs/operations-handoff.md`.

Use `docs/new-site-checklist.md` as the working record and follow its links to `docs/quickstart.md` for the Sanity, Pages, publishing, alert and Resend procedures. Keep all secrets in account secret stores, not examples, issues, logs, screenshots or commits. Review the complete tracked-file list before pushing a public client repository. Commit narrowly and preserve unrelated work.
